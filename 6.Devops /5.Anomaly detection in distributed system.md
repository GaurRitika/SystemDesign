##  PHASE 1 — What is Anomaly Detection?

**Definition:**

> Anomaly detection in distributed systems means identifying behavior that *deviates significantly from normal system patterns.*

This includes:

* Latency spikes 
* Sudden increase in error rates 
* Drop in throughput 
* Unusual CPU/memory usage 
* Irregular network traffic 

So basically, the system “learns” what normal looks like — and **flags deviations** before they cause cascading failures.

---

##  PHASE 2 — Why It’s Important in Distributed Systems

Distributed systems = hundreds of microservices, each on multiple servers.
Failures don’t happen as “server crash” only — they often start subtly:

| Small anomaly                    | Later effect                             |
| -------------------------------- | ---------------------------------------- |
| 2× latency increase in 1 service | Queue backlog grows                      |
| High error rate from 1 pod       | Load balancer overcompensates            |
| CPU spikes in 1 node             | Other nodes start throttling             |
| Network jitter                   | Requests timeout → retries flood network |

Without detection, these “weak signals” can snowball into **cascading failures** or **outages**.

Anomaly detection = *early warning radar* of the distributed world 🚨

---

##  PHASE 3 — What “Anomalies” Look Like (Types)

| Type                   | Description                          | Example                                  |
| ---------------------- | ------------------------------------ | ---------------------------------------- |
| **Point anomaly**      | Single unexpected data point         | Latency = 2s (avg is 100ms)              |
| **Contextual anomaly** | Unusual given context (time, region) | CPU spike during midnight (normally low) |
| **Collective anomaly** | Unusual pattern over time            | Gradual increase in errors over 10 min   |

These are typically detected on **metrics** (CPU, latency, QPS, error rate, memory, etc.) or **logs**.

---

##  PHASE 4 — How Anomaly Detection Works (Conceptually)

Every service, container, or node emits **metrics + logs** continuously:

```
timestamp | service | metric_type | value
-----------------------------------------
12:00:00  | auth     | latency_ms  | 80
12:00:01  | auth     | latency_ms  | 81
12:00:02  | auth     | latency_ms  | 250   <-- anomaly
```

### The pipeline:

1. **Data Collection**

   * Gather metrics/logs/traces
   * Tools: Prometheus, OpenTelemetry, Fluentd, Datadog, Grafana

2. **Data Aggregation**

   * Combine data from multiple nodes/services
   * Store in time-series DB (like InfluxDB, Prometheus TSDB)

3. **Baseline Modeling**

   * Define “normal” based on history:

     * Mean/Std deviation
     * Seasonality patterns
     * Machine learning models

4. **Anomaly Detection Algorithm**

   * Detect sudden deviations from baseline

5. **Alerting + Auto-Action**

   * Trigger alert → PagerDuty, Slack, or auto-healing script
   * Optionally scale, restart, or reroute traffic

---

##  PHASE 5 — Core Detection Techniques (from simple → advanced)

| Technique                                        | Type          | Concept                                     | Example Use                 |
| ------------------------------------------------ | ------------- | ------------------------------------------- | --------------------------- |
| **Static Thresholds**                            | Rule-based    | If CPU > 90% → alert                        | Simple but noisy            |
| **Moving Average / Std Dev**                     | Statistical   | If latency > 3σ from mean                   | Detects spikes              |
| **EWMA (Exponentially Weighted Moving Average)** | Statistical   | Weigh recent data more                      | Smooth trend                |
| **ARIMA / Holt-Winters**                         | Time-series   | Predict expected value based on past        | Detect seasonal anomalies   |
| **Isolation Forests**                            | ML-based      | Randomly isolate data points                | Detect outliers             |
| **LSTM Autoencoders**                            | Deep learning | Learn normal sequence behavior              | Detect complex patterns     |
| **Graph-based Anomaly Detection**                | Advanced      | Detect unusual behavior in dependency graph | Service call graph analysis |

##  PHASE 6 — Example (Netflix’s Latency Anomaly Detection)

Imagine Netflix has microservices like:

```
[Auth] → [User] → [Catalog] → [Playback]
```

Let’s say:

* Normal latency between Auth → User = 100ms
* Suddenly spikes to 800ms

### Detection Flow:

1. Each service emits latency metrics via **Atlas (Netflix’s telemetry system)**
2. Metrics go to a **central collector**
3. Statistical model (e.g., 3σ deviation) detects abnormal latency
4. Alert triggered:

   * "User service latency > 700ms (8× baseline)"
5. Auto-remediation:

   * Load balancer stops routing new traffic to slow instance
   * System scales up new instances

 Anomaly detected early → prevented outage.

---

##  PHASE 7 — Example: Using a Database as Message Source

For example, if the system uses Kafka:

* Each service emits metrics/logs into **Kafka topics**
* A separate **Anomaly Detection Consumer** subscribes
* It applies ML/statistical checks in near real-time
* Pushes detected anomalies to an alert topic or monitoring dashboard

This is how **event-driven anomaly detection** is done in real-time architectures.

##  PHASE 9 — Advanced: Correlation & Root Cause Analysis

Once an anomaly is detected, we also need to find **why** it happened.

Example:

* `Feed-Service` latency spike.
* System auto-checks correlated anomalies:

  * `User-Service` CPU spike at same time → likely cause.

This is **Root Cause Correlation**, often done using:

* **Graph-based dependency tracing (OpenTelemetry)**
* **Trace ID propagation**
* **Causal graph models (e.g., Bayesian Networks)**

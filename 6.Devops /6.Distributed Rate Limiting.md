##  What Is Rate Limiting?

Rate limiting means **controlling how many requests a user, service, or IP address can make within a given time window.**

For example:

> API allows max **100 requests per minute per user** — if exceeded → block or delay.

---

##  Why Do We Need Rate Limiting?

### 1. Prevent system overload

* Stops a sudden flood of requests (intentional or unintentional).
* Protects downstream databases and APIs from being overwhelmed.

### 2. Fair usage

* Prevents one user from consuming all resources.
* Ensures **QoS (Quality of Service)** for all users.

### 3. Prevent abuse

* Stops brute-force login attempts.
* Stops API misuse, scrapers, bots, DDoS attacks.

---

##  Core Idea

Every time a request comes in:

1. Identify the **client** (API key, userID, IP).
2. Check how many requests the client has made in the current time window.
3. Allow or reject the request based on the configured limit.

---

##  Basic Algorithms

| Algorithm          | How it works                                             | Pros                                            | Cons                                     |
| ------------------ | -------------------------------------------------------- | ----------------------------------------------- | ---------------------------------------- |
| **Fixed Window**   | Count requests in discrete windows (e.g., 1 min blocks). | Simple                                          | Spike at boundary (reset every minute).  |
| **Sliding Window** | Smooths over the last N seconds/minutes.                 | Fairer                                          | Slightly complex.                        |
| **Token Bucket**   | Add tokens at a fixed rate; each request consumes one.   | Allows short bursts, very common in production. | Needs sync of token counts across nodes. |
| **Leaky Bucket**   | Queue requests and process at fixed rate.                | Smooth traffic                                  | Adds latency, not ideal for real-time.   |

---

##  Distributed Rate Limiting — The Real Challenge

In **distributed systems**, there are many servers handling requests.

If each node enforces rate limits **independently**, users can **bypass limits** by hitting multiple servers.

So we need a **centralized or coordinated limit enforcement** across all instances.

---

##  Example: Distributed Rate Limiting in a Microservices Architecture

Imagine:

* You have **10 API servers**.
* Each handles requests for `api.instagram.com`.

We want:

> Limit: **100 requests per user per minute**, globally.

Now, how do we track a user’s request count across all servers?

---

##  Common Implementation Approaches

### **1️⃣ Centralized Counter using Redis**

**Flow:**

1. Every API server connects to a shared Redis cluster.
2. When a request comes:

   * Increment a key: `rate_limit:{user_id}`.
   * Redis key has TTL = 60 seconds.
3. Redis atomically counts requests.
4. If count > limit → reject.

✅ **Advantages:**

* Consistent global state.
* Redis is fast (in-memory, O(1) ops).

⚠️ **Disadvantages:**

* Redis becomes a single point of failure or bottleneck.
* Must be scaled and replicated properly.

📦 Example Key in Redis:

```
rate_limit:user123 -> 54 (expires in 25s)
```

---

### **2️⃣ Distributed Token Bucket (Using Redis or Memcached)**

Each user has a bucket:

* Add tokens at constant rate.
* Each request consumes a token.
* If bucket empty → reject.

You can implement this **using Redis Lua scripts** to ensure atomic updates.

---

### **3️⃣ Client-Side Rate Limiting (Edge + CDN)**

At large scale (e.g., Instagram/Netflix):

* Rate limits are applied **closer to the user** — at **CDN edge** (like Cloudflare or Akamai).
* Prevents even hitting your core servers.

✅ Pros:

* Protects infrastructure early.
* Reduces traffic before reaching backend.

---

### **4️⃣ Hierarchical Rate Limiting**

Combination of multiple levels:

* **User-level** → per user/API key.
* **IP-level** → to stop spam or DDoS.
* **Service-level** → total request cap per API.

---

## 🔄 Replication + Failover

* Redis or rate limit service is usually deployed as **primary + replica nodes**.
* Use **replication** to maintain availability.
* If one Redis node fails → automatically failover to replica.
* To avoid stale counts → use quorum writes or consistency checks (e.g., Redis Cluster or DynamoDB).

---

##  Avoiding Common Pitfalls

| Problem                    | Solution                                                |
| -------------------------- | ------------------------------------------------------- |
| **Hot key (popular user)** | Use sharded Redis clusters (consistent hashing).        |
| **Clock skew**             | Use relative timestamps or monotonic clocks.            |
| **Redis overload**         | Add local caching + batching.                           |
| **Multi-region system**    | Keep regional rate limiters + global sync periodically. |

## 📊 Example Visualization (Instagram API)

| Step | Component     | Action                                |
| ---- | ------------- | ------------------------------------- |
| 1    | User          | Sends request to `/api/upload`        |
| 2    | Load Balancer | Routes to nearest API node            |
| 3    | API Server    | Checks Redis for `rate_limit:user_id` |
| 4    | Redis Cluster | Returns current count                 |
| 5    | API Server    | If under limit → process, else reject |
| 6    | Redis TTL     | Resets count after 1 minute           |

## 🚀 Advanced: Rate Limiting as a Service

Companies like **Stripe, Cloudflare, and AWS** build **Rate Limiting Microservices**:

* Handles distributed state.
* Provides APIs like `/check_limit(user_id)`.

They often use:

* **Redis Cluster or DynamoDB** as backend.
* **gRPC** or **HTTP APIs** for fast communication.
* **Prometheus + Grafana** for monitoring usage.

##  What Is a Cache (Quick Recap)

A **cache** is a small, high-speed storage layer that keeps *frequently accessed data* close to the application — to reduce **latency** and **database load**.

Example:

> Instead of hitting the main DB every time a user opens Instagram, store their profile data in cache for a few minutes.

---

##  What Is Distributed Caching?

When your system grows — one cache server isn’t enough.
So you use **multiple cache servers** distributed across nodes or data centers.

👉 **Distributed Caching** = Using a cluster of cache nodes that together behave like one big cache.

---

##  Purpose

* Reduce **database hits**
* Improve **latency** (microseconds vs milliseconds)
* Handle **massive scale** (millions of requests/sec)
* Provide **fault tolerance and scalability**

---

##  Example (Instagram-Style)

### Without Cache:

1. User requests profile `GET /user/gaur`.
2. Server queries the **database**.
3. DB returns user data (slow, 100ms).
4. Server sends response.

→ For 10 million users, this crushes the DB.

---

### With Distributed Cache:

1. User requests `GET /user/gaur`.
2. Server first checks **cache cluster** (Redis/Memcached).

   * If **hit** → return instantly (1–2ms).
   * If **miss** → query DB, then **store** in cache for next time.

This reduces DB load massively.

##  Popular Distributed Cache Systems

| Cache                     | Description                                                                       |
| ------------------------- | --------------------------------------------------------------------------------- |
| **Redis Cluster**         | In-memory key-value store, supports persistence, replication, Lua scripting, etc. |
| **Memcached**             | Pure in-memory, simple key-value store, very fast.                                |
| **Hazelcast / Ehcache**   | Used in Java enterprise systems.                                                  |
| **Aerospike / Couchbase** | Enterprise-grade distributed caches with disk persistence.                        |

##  Architecture — Distributed Cache Cluster

Imagine 4 cache nodes:

```
Cache Cluster:
  ├── Node 1
  ├── Node 2
  ├── Node 3
  └── Node 4
```

Each node stores *a subset* of keys.

The app uses **consistent hashing** (remember that?) to decide:

> Which node stores which key.

So when you do:

```bash
SET user:123 = {profile_data}
```

Consistent hashing maps `user:123` → Node 2.

---

## 🔄 Data Flow (Example)

**Step-by-step when a user requests a profile:**

1️⃣ API server receives request `/profile?id=123`
2️⃣ API server computes hash → maps to **Cache Node 2**
3️⃣ Cache lookup:

* If found → return immediately ✅
* If not found → query DB ❌
  4️⃣ Store DB result back into cache (`SET user:123 = ...`)
  5️⃣ Serve response to user.

##  Cache Aside Pattern (Most Common)

**Used by Instagram, Netflix, Twitter**

```text
read(key):
  if key in cache:
    return cache[key]
  else:
    data = db.read(key)
    cache[key] = data
    return data
```

**write(key, value):**

* Update DB first.
* Then delete cache entry (so next read fetches fresh value).

This pattern keeps DB as *source of truth*.

---

##  Write Policies

| Policy                        | Description                             | Used When                                          |
| ----------------------------- | --------------------------------------- | -------------------------------------------------- |
| **Write-Through**             | Write to cache **and** DB at same time. | When data consistency is critical.                 |
| **Write-Back (Write-Behind)** | Write to cache first, DB later (async). | High performance, eventual consistency acceptable. |
| **Write-Around**              | Skip cache on writes, only cache reads. | For rarely-read data.                              |

---

## ⚙️ Handling Consistency Issues

**Cache Invalidation** = one of the hardest problems.

When DB updates, cache might have *stale data*.

✅ Solutions:

* **TTL (Time-To-Live)**: auto-expire entries after N seconds.
* **Write-through policy**: update cache immediately.
* **Message Queue invalidation**: publish invalidation event to all cache nodes.

---

## Data Replication in Distributed Cache

To ensure reliability:

* Each cache node has a **replica**.
* If Node 2 fails → replica takes over.
* Data replicated asynchronously or synchronously.

Redis Cluster uses **Master-Replica** setup:

```
Master 1 → Replica 1a
Master 2 → Replica 2a
```

---

##  Multi-Region Caching

For global systems like Netflix:

* Cache layers exist **per region (e.g., US-East, EU-West)**.
* Some global data replicated across regions.
* Local cache → region DB → global DB.

---

##  Eviction Policies (When Cache Full)

| Policy                          | Description                          |
| ------------------------------- | ------------------------------------ |
| **LRU (Least Recently Used)**   | Remove least recently accessed keys. |
| **LFU (Least Frequently Used)** | Remove least frequently used keys.   |
| **FIFO**                        | Remove oldest keys.                  |
| **Random**                      | Randomly evict.                      |
| **TTL-based**                   | Auto-expire after a given time.      |

Redis supports all of these.

##  Example — Instagram Feed Cache

1️⃣ Feed service fetches 100 latest posts for user.
2️⃣ Caches it as:

```
feed:user123 → [postA, postB, postC]
```

3️⃣ On next refresh:

* Directly return cached feed (1–5ms).
* Background worker updates feed periodically.

This avoids recalculating the feed every time (which is expensive).

##  Optimization Techniques

| Technique                | Benefit                                   |
| ------------------------ | ----------------------------------------- |
| **Local + Global cache** | Combine local (in-process) + Redis cache. |
| **Sharded caching**      | Split data by userID or hash.             |
| **Batch warmup**         | Preload popular data into cache.          |
| **Lazy loading**         | Load data only when needed.               |
| **Async refresh**        | Refresh expired data in background.       |

---

##  Common Problems

| Issue                  | Description                                   | Fix                               |
| ---------------------- | --------------------------------------------- | --------------------------------- |
| **Cache stampede**     | Many requests miss at once (thundering herd). | Use locking or jitter TTL.        |
| **Hot keys**           | Some keys get too many hits.                  | Shard or replicate hot keys.      |
| **Data inconsistency** | Cache not invalidated after DB update.        | TTL + proper invalidation flow.   |
| **Node failure**       | Data on that node lost.                       | Replication + consistent hashing. |

##  Real-Life Example (Instagram Feed)

| Step | Component    | Description                      |
| ---- | ------------ | -------------------------------- |
| 1    | Client       | Opens Instagram feed             |
| 2    | API Gateway  | Routes to nearest region         |
| 3    | Feed Service | Checks cache (Redis Cluster)     |
| 4    | Redis        | Returns cached feed if available |
| 5    | DB           | Queried only if cache miss       |
| 6    | Cache Write  | Stores feed for next request     |

→ Most feed requests hit Redis, not DB = huge speedup.
